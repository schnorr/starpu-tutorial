* Part A — Heterogeneous codelets: CPU and GPU (~45 min)
** Recap: what a codelet's "implementations" are

A StarPU codelet can list more than one implementation of the same
computation — e.g. =.cpu_funcs = { impl_a, impl_b }=, or, as you'll see
in the instructor demo, both =.cpu_funcs= *and* =.cuda_funcs=. StarPU's
scheduler decides, per task, which available worker (and hence which
implementation) actually executes it. Today's exercise builds the
*CPU-only* half of that idea: give the same codelet two CPU
implementations, and confirm StarPU still runs it correctly.

** Starting point: block matrix multiplication

We reuse the block matrix multiplication example, provided at
=code/exercise/multi_matrix.c= on the host
(=mount/exercise/multi_matrix.c= inside the container), with a
=Makefile=: a 1000x1000 matrix split into 200x200 blocks (5x5 grid),
computing =C = A * B= block by block with one task per =(i, j, k)=
combination (this is why there are more tasks than blocks in =C= — each
output block accumulates contributions from =NUMBER_BLOCKS_WIDTH=
tasks).

Build and run it as-is first, before you touch anything:

#+begin_src bash
cd mount/exercise
make
./multi_matrix
#+end_src

Every printed value should be =2000.000000=: each element of =C= is the
sum, over all =MATRIX_WIDTH= (1000) positions of the shared dimension,
of =A[.]*B[.] = 1*2=, i.e. =1000 * 2 = 2000= — the blocking just splits
that sum across =NUMBER_BLOCKS_WIDTH= (5) tasks per output block, each
contributing a partial sum over its local =BLOCK_WIDTH= (200) elements.
The point of this check is "no leftover zeros, no NaNs, all blocks
consistent" before you start editing the codelet.

** Exercise: add a second CPU implementation

In =multi_matrix.c=, the codelet is:

#+begin_src c
struct starpu_codelet codelet_multi =
{
    .cpu_funcs = { func_cpu },
    .cpu_funcs_name = { "func_cpu" },
    .nbuffers = 3,
    .modes = { STARPU_R, STARPU_R, STARPU_W },
	.where = STARPU_CPU,
	.name = "multiplica_bloco"
};
#+end_src

** Instructor demo: adding the GPU implementation
*** Running the container with GPU access (instructor only)

One-time setup on the GPU machine (only needed once, not per session):
generate the NVIDIA CDI spec so Podman/Docker can see the GPU at all —
without this, =--device=/=--gpus= silently finds nothing:

#+begin_src bash
sudo nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml
sudo chmod a+r /etc/cdi/nvidia.yaml
#+end_src

Then start the container the same way as the student flow above, just
adding =--device nvidia.com/gpu=all=:

#+begin_src bash
podman run -it --userns=keep-id --device nvidia.com/gpu=all \
    --mount type=bind,src="$(pwd)/code",target=/home/starpu/mount \
    registry.gitlab.inria.fr/starpu/starpu-docker/starpu:1.4.7
#+end_src

Confirm StarPU actually sees the GPU before going further:

#+begin_src bash
starpu_machine_display -notopology
#+end_src

Look for a line like "1 CUDA worker: CUDA 0.0 (<your GPU name>)". If it
says "No CUDA worker" instead: check =nvidia-smi -L= on the *host*
first — if that doesn't list the GPU either, the container flags won't
help, the problem is outside the container. If =nvidia-smi -L= *does*
work on the host, re-check the CDI step above (=nvidia-ctk cdi list=
should print =nvidia.com/gpu=all= and at least one indexed device) and
that =--device nvidia.com/gpu=all= was actually passed to this specific
=run= command — an existing container started without it does not pick
up the GPU retroactively; start a new one.

*** Warm-up: do this *before* the audience is watching

The *first* time any CUDA program runs inside a given container, StarPU
prints "No performance model for the bus, calibrating..." and spends
*60-90 seconds* actually measuring host↔GPU transfer bandwidth — it
looks like the program hung, it did not. This calibration result is
cached under =~/.starpu/= *inside the container's own filesystem*, so:
- Running the demo a second time *in the same container* is near-instant
  (well under a second) — no calibration message, cache hit.
- Exiting the container (or using =--rm= and starting a fresh one, as
  above) throws that cache away, so the *next* container's first CUDA
  run pays the same 60-90s again.

So: right after starting the container above, build and run the demo
*once* before the session (or before the audience is looking at the
screen) to pay that cost up front, then keep *that same* container/shell
open for the actual live demo — don't exit and restart it between runs,
or you will be back to a silent 60-90s wait live on stage.

#+begin_src bash
cd mount/demo
make
./soma_matrix_cuda   # first run: ~60-90s, "calibrating..." — do this before the audience arrives
./soma_matrix_cuda   # second run, same container: near-instant — this is what to demo live
#+end_src

*** The demo itself

The instructor now shows the CUDA counterpart of the *addition* example
(a simpler kernel than multiplication, chosen so the demo stays short),
provided at =code/demo/soma_matrix_cuda.c= on the host
(=mount/demo/soma_matrix_cuda.c= inside the container, with a
=Makefile=) — already built and warmed up above, so =./soma_matrix_cuda=
from here on returns instantly:

#+begin_src c
struct starpu_codelet codelet_soma =
{
    .cpu_funcs = { func_cpu },
    .cuda_funcs = { func_gpu },
    .nbuffers = 3,
    .modes = { STARPU_R, STARPU_R, STARPU_W },
    .name = "soma_bloco",
    .where = STARPU_CUDA
};
#+end_src

Watch for:
- =func_gpu= is the same "C = A + B" computation as =func_cpu=, but
  written against cuBLAS (=cublasSgeam=) and running on the StarPU CUDA
  stream (=starpu_cuda_get_local_stream()=).
- =.where = STARPU_CUDA= here means *only* the GPU implementation is
  eligible in this exact struct — contrast with your exercise, where
  =.where = STARPU_CPU= restricted to CPU. The instructor will also show
  the version with =.where= left out (both =.cpu_funcs= and
  =.cuda_funcs= set, no =.where=), where StarPU is free to choose either
  a CPU or a GPU worker per task.
- The instructor times the same program run three ways (CPU-only build,
  GPU-only build, and letting StarPU choose) and compares wall-clock
  time. You are not expected to reproduce this — no GPU is assumed on
  your machine — just observe and ask questions.

*Note on the official, production-grade version*: what you just saw is
the simplest possible CPU-vs-GPU codelet, chosen so the concept stays
visible. StarPU's own tutorial ships a realistic equivalent that calls
into real BLAS/cuBLAS/hipBLAS libraries for actual GEMM (matrix-matrix
product) — not included in this package, but worth looking up after the
tutorial to see "what this looks like for a real numerical kernel". It
is not live-coded here since the Makefile/BLAS-backend plumbing would
eat the time budget.

* Part B — Execution traces and StarVZ visualization (~45 min)

Goal: stop guessing which worker ran which task, and *see* it — using
the same programs you already ran in Part A (and Session 2) as trace
sources.

** Recording a trace

StarPU must be built with FxT tracing support (already the case in the
tutorial Docker image). Enable it with two environment variables, then
rerun any program you already built:

#+begin_src bash
STARPU_FXT_TRACE=1 STARPU_GENERATE_TRACE=1 STARPU_FXT_PREFIX=$PWD/ ./multi_matrix
#+end_src

=STARPU_FXT_TRACE=1= is the one that actually turns tracing *on* — it is
easy to miss, and without it no trace file is produced at all, no
error either. This produces one or more =prof_*= files (the *raw* FxT
trace) in =STARPU_FXT_PREFIX= — one per StarPU main thread. That is
the only input Phase 1 below needs; set =STARPU_GENERATE_TRACE=1= here —
that flag makes StarPU run its own copy of =starpu_fxt_tool= at
shutdown. This step might be invoked by StarVZ Phase on the same raw
trace, however, it requires a compatible StarPU build at the StarVZ
container, which is not the case here.

** Phase 1 — convert the raw trace 

The option =--use-paje-trace= skips the local call of =starpu_fxt_tool=
since it is already accomplished by =STARPU_GENERATE_TRACE=1= in the
previous step.
#+begin_src bash
starvz --use-paje-trace --keep --phase1 ./
#+end_src

This turns the =prof_*= FxT files into =.parquet= files (columnar data,
readable from R) in the same directory.

** Phase 2 — load, configure, and plot (in R)
The =starvz= wrapper can produce a standard visualization in PDF without
navigate in the R console.
#+begin_src bash
starvz --phase2 --save starvz_plot.pdf ./
#+end_src

The default visualization can be customized by executing the second
step directly in R. StarVZ enables a set of different plots that can
be configured on a .yaml file. A default file is provided
(default.yaml); also, the options can be changed directly in R.

#+begin_src R
library(starvz)
library(dplyr)

dtrace <- starvz_read("./", selective = FALSE)
#+end_src

Turn on the panels that matter most for a first look — submitted vs.
ready task curves (this is what answers "was there ever an idle
worker with tasks piling up ready to run?"):

#+begin_src R
dtrace$config$starpu$active = FALSE
dtrace$config$submitted$active = TRUE
dtrace$config$submitted$height  = 1
dtrace$config$ready$active = TRUE
dtrace$config$ready$height  = 1
dtrace$config$st$labels = "ALL"
#+end_src

Then render it:

#+begin_src R
starvz_plot(dtrace)
#+end_src

You should get a space-time diagram similar to
=../session1/img/starvz.png= — one row per worker, colored rectangles
for each task execution, plus the submitted/ready curves above.
