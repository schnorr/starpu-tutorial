** The two images

The commands below refer to the images through two variables; set them

Check whether they are already on the machine:

#+begin_src bash

#+end_src

If not, load them *first thing*, since it takes several minutes; the
rest of the opening can go on meanwhile. Use one of the three ways
below, in this order of preference:

   (=starpu-image.tar.zst= and =starvz-image.tar.zst=):

The archives keep the image names, so the =STARPU_IMG= and =STARVZ_IMG=

** Get the material

#+begin_src bash
git clone https://github.com/schnorr/starpu-tutorial.git
cd starpu-tutorial
#+end_src

** Start the StarPU container (terminal 1)

From the =starpu-tutorial= directory:

#+begin_src bash
podman run -it --userns=keep-id --hostname starpu \
    --mount type=bind,src="$(pwd)",target=/home/starpu/mount \
    $STARPU_IMG
#+end_src

- =--mount= makes the repository visible inside the container as
  =~/mount=: files you edit on the host (with your usual editor) are
  the same files the container compiles and runs.
- =--userns=keep-id= keeps your own user ID inside the container, so
  the container can write into the mounted directory. Without it,
  rootless Podman remaps the IDs and the build fails with "Permission
  denied".
- =--hostname starpu= gives the container a fixed name; StarPU stores
  its performance models per host name.

*Keep this shell open until the end*: the performance models that
StarPU calibrates during Hands-on 2 live inside this container.

Check that StarPU sees the CPUs:

#+begin_src bash
starpu_machine_display -notopology
#+end_src

You should see one CPU worker per core (6 on the Lab DIMAp machines).
If you see twice as many as physical cores, read "Workers and cores"
in Hands-on 2.

Goal: build and run the first two StarPU programs of the chapter

** Build all the examples

In terminal 1 (StarPU container):

#+begin_src bash
cd ~/mount/examples

#+end_src

** =hello_world=: four tasks

Read =hello_world.c= (Listing 3.4 of the chapter): one codelet with a
single CPU implementation, four tasks, no data. Run it with different
numbers of CPU workers:

#+begin_src bash
time STARPU_NCPU=1 ./hello_world
time STARPU_NCPU=4 ./hello_world
#+end_src

*Questions*:
- Each task sleeps one second. Explain the two execution times.
- Run it several times with =STARPU_NCPU=4=. Is the order of the lines
  always the same? Are the worker numbers? Why?
- What does =starpu_task_wait_for_all()= wait for? What happens to the
  output if you remove it? (Try it.)

** =vector_scal=: two tasks on the same data

Read =vector_scal.c= (Listing 3.6): the vector is /registered/ with
StarPU, and two tasks scale it by 2 and by 3, both in =STARPU_RW=
mode.

#+begin_src bash
./vector_scal
#+end_src

*Questions*:
- The program prints =vector[0] = 6.0=. Which dependency (RAW, WAR,
  WAW) did StarPU infer between the two tasks? Where is it written in
  the code?
- Why must the program call =starpu_data_unregister()= before reading
  =vector[0]=?
- The factor is passed with =STARPU_VALUE=, the vector with a data
  handle. What is the difference for the runtime?

** Block size and scheduler (12 min)

Use the reference program from now on, with 6 CPU workers and the
model-based scheduler =dmda=:

#+begin_src bash
export STARPU_NCPU=6 STARPU_SCHED=dmda
./gemm_starpu 2048 8     # first runs calibrate the performance model
./gemm_starpu 2048 8
./gemm_starpu 2048 2
#+end_src

*Questions*:
- With $NB = 2$, the DAG (Figure 3.1) has four independent chains of
  two tasks. How many of the six workers can be busy at the same time?
  Compare the GFlop/s of $NB = 2$ and $NB = 8$.
- Try $NB$ = 4, 16, 32 and 64. Where is the best performance? Why does
  it drop again for very small blocks?

  #+begin_src bash
  for nb in 2 4 8 16 32 64; do ./gemm_starpu 2048 $nb; done
  #+end_src

- Compare the greedy scheduler with the model-based one. Is there a
  difference on a machine with only CPUs? Why?

  #+begin_src bash
  STARPU_SCHED=eager ./gemm_starpu 2048 8
  STARPU_SCHED=dmda  ./gemm_starpu 2048 8
  #+end_src

Look at what =dmda= learned:

#+begin_src bash
starpu_perfmodel_display -s gemm
#+end_src

Each line is one block size (=size= is the bytes of the three blocks),
with the mean duration in microseconds and the number of samples. Check
that a block product of order 1024 takes about $64$ times longer than
one of order 256: why 64? (=starpu_perfmodel_plot -s gemm= writes a
gnuplot script, =starpu_gemm.gp=, which you can plot on the host if
gnuplot is installed.)

** Workers and cores

StarPU creates one CPU worker per core it detects. On a processor with
two hardware threads per core, or with cores of different kinds, it may
place two workers on the same physical core, which halves the speed of
both. =starpu_machine_display= shows the binding; when it is wrong,
=STARPU_WORKERS_CPUID= lists the logical CPUs to use, one per worker.
For instance, on the instructor's laptop (logical CPUs $2c$ and $2c+1$
share core $c$):

#+begin_src bash
STARPU_WORKERS_CPUID="0 2 4 6 8 10" ./gemm_starpu 2048 8
#+end_src

On the Lab DIMAp machines (6 physical cores, no hardware threads),
nothing is needed.

** Instructor demo: the same binary with a GPU (5 min)

Run on the instructor's machine only, projected. The CUDA
implementation of =gemm_cl= (Listing 3.8) calls =cublasSgemm=; the same
=gemm_starpu= binary uses it as soon as a GPU is visible.

#+begin_src bash
podman run -it --userns=keep-id --hostname starpu-demo \
    --device nvidia.com/gpu=all \
    -v starpu-calib:/home/starpu/.starpu:U \
    -v starpu-nvcache:/home/starpu/.nv:U \
    --mount type=bind,src="$(pwd)",target=/home/starpu/mount \
    $STARPU_IMG
cd ~/mount/examples && make
starpu_machine_display -notopology     # "1 CUDA worker"
export STARPU_NCPU=6
STARPU_SCHED=dmda  ./gemm_starpu 2048 8    # CPUs + GPU
STARPU_NCUDA=0     ./gemm_starpu 2048 8    # CPUs only
STARPU_NCPU=0      ./gemm_starpu 2048 8    # GPU only
STARPU_SCHED=eager ./gemm_starpu 2048 8    # CPUs + GPU, greedy
#+end_src

What to show: with =dmda= and a calibrated model, all the tasks go to
the GPU (about 370 GFlop/s on the instructor's RTX A1000, against about
10 GFlop/s on 6 CPU workers); with =eager=, the CPU workers grab a few
tasks that they execute about 200 times slower than the GPU (16 ms
against 0.09 ms), and the GPU ends up waiting for them. Hands-on 3 shows the two traces.

* Hands-on 3 (15:35, 25 min): traces and StarVZ

Goal: record the traces of $NB = 2$ and $NB = 8$, and reproduce the
figure of Section 3.5 (Figure 3.3) on your own machine.

** Record the traces (StarPU container, 5 min)

In terminal 1, still with =STARPU_NCPU=6= and =STARPU_SCHED=dmda=:

#+begin_src bash
cd ~/mount/examples
for nb in 2 8; do
    mkdir -p trace_nb$nb
    (cd trace_nb$nb && \
     STARPU_FXT_TRACE=1 STARPU_GENERATE_TRACE=1 STARPU_FXT_PREFIX=$PWD/ \
         ../gemm_starpu 2048 $nb)
done
ls trace_nb8
#+end_src

- =STARPU_FXT_TRACE=1= turns the recording on; without it, no trace
  and no error.
- =STARPU_FXT_PREFIX= is where the raw FxT file (=prof_file_*=) goes.
- =STARPU_GENERATE_TRACE=1= converts it at =starpu_shutdown()= into
  =paje.trace=, =tasks.rec=, =dag.dot=... in the /current/ directory,
  hence the =cd=. The StarVZ container cannot do this conversion
  itself: it has no =starpu_fxt_tool= matching this StarPU.

This differs from Listings 3.11 and 3.12 of the chapter, which assume
StarPU and StarVZ installed on the same machine: there, StarVZ Phase 1
calls =starpu_fxt_tool= itself on the raw trace. With two separate
containers, the conversion has to happen in the StarPU one.

** Start the StarVZ container (terminal 2)

Open a second host terminal, go to the =starpu-tutorial= directory,
set =STARVZ_IMG= again, and run:

#+begin_src bash
podman run -it --rm --userns=keep-id --entrypoint bash \
    --mount type=bind,src="$(pwd)",target=/home/rstudio/mount \
    $STARVZ_IMG
alias starvz=$(Rscript -e 'cat(system.file("tools", package="starvz"))')/starvz
cd ~/mount/examples
#+end_src

The image starts a shell that ignores its arguments, hence
=--entrypoint bash=. The =starvz= script comes with the R package; the
alias puts it at hand.

** Phase 1 and Phase 2 (10 min)

#+begin_src bash
starvz --use-paje-trace --keep --phase1 trace_nb2/
starvz --use-paje-trace --keep --phase1 trace_nb8/
Rscript starvz_compare.R starvz_compare.yaml trace_nb2 trace_nb8 starvz_nb2_nb8.png
#+end_src

- =--use-paje-trace= starts from the =paje.trace= produced by StarPU
  instead of calling =starpu_fxt_tool=; =--keep= keeps it.
- Phase 1 writes the =.parquet= files next to the trace.
- =starvz_compare.R= reads both traces with the configuration
  =starvz_compare.yaml= (Listing 3.13) and draws them side by side, on
  the same time axis.

Open =examples/starvz_nb2_nb8.png= on the host with any image viewer.

If something went wrong with your traces, use the ones recorded by the
instructor, already through Phase 1:

#+begin_src bash
Rscript starvz_compare.R starvz_compare.yaml ../traces/nb2 ../traces/nb8 starvz_nb2_nb8.png
#+end_src

** Reading the figure (10 min)

*Questions*:
- With $NB = 8$, how long does it take to submit the 512 tasks,
  compared with the execution? How many tasks are ready during most of
  the run, and why that number?
- With $NB = 2$, how many tasks are ever ready? How many run at the
  same time? Some workers may be missing from the figure: StarVZ only
  shows workers that executed at least one task. How many are missing
  on your machine?
- The gray band is the ABE bound, computed from the task durations
  ignoring dependencies. Why is the $NB = 2$ makespan far from it, and
  the $NB = 8$ makespan almost on it?
- The idleness percentage is on the left of each row. Which
  configuration wastes the machine, and where does the waste come
  from: the runtime, the data transfers, or the DAG?
